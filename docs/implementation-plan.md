# 구현 계획

## 1. 문서 선행

실제 페이지·ZIP을 조사해 확인한 사실과 설계·미확정 사항을 분리한다.
KRIC의 구조, Opinet의 async 패턴, MOIS 파일 API, transport 매핑 원칙,
geo GDAL binding 활용을 반영한다. 사양과 작업 목록을 먼저 PR로 머지한다.
그 전에는 provider 구현 코드를 만들지 않는다. 조사 재현 도구만 허용한다.

## 2. 구현 의존 순서

T002 패키지/async session → T003 카탈로그/다운로드 → T004 GDAL loader →
T005 선착장/매핑 → T006 파일 보관 → T007 공개 웹 기능 확대 → T008 전체 수용 순서다.
사용자 추가 요청에 따라 T007은 A(OpenAPI/자료실)와 B(추가 관광자료)로 나눴다.
T007B는 숙박·체험·해수욕장·마리나 등 실제 가용자료를 조사해 유용한 자료를 구현한다.
각 단계의 독립 PR이 머지되기 전 다음 단계의 구현에 착수하지 않는다.
현재 상태는 [작업 목록](tasks.md), 재개 위치는 [resume](resume.md)을 기준으로 한다.

## 3. 원천 제약 처리

여객터미널 다운로드 미제공과 도선 출도착지 부재는 구현 결함과 다른 원천 제약이다.
오류/상태·로컬 원문·명시적 보강 인터페이스를 구현하되, 근거가 없으면 실제 제공 완료를
주장하지 않는다. T005E에 독립 관리하고 다음 단계에서도 제약을 보존한다.
관광지정보의 여객선은 선착장 후보 원천으로 제공하며 여객터미널 대신이라고 표기하지 않는다.

## 4. PR별 gate

1. `origin/main` 동기화 후 작업 브랜치와 Draft PR.
2. scope에 맞는 unit·typecheck·패키지 검사 및 실제 live E2E.
3. 독립 적대적 리뷰어 2명, P0~P2 수정과 재리뷰.
4. 최종 구현 SHA와 증빙·원격 CI 확인 후 ready 전환·SHA 고정 머지.
5. 원격 main의 merge commit 확인, task 완료·journal/resume 반영 후 다음 task.

구체적인 증빙은 [runbook](runbooks/hostile-review.md)에 따른다.
